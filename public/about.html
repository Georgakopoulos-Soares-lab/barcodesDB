About barcodesDB

What is barcodesDB?

barcodesDB is a high-performance database of DNA barcodes — short k-mer sequences (k = 16, 17, or 18) that are absent from known genomic sequences. These sequences can serve as molecular tags, identifiers, or probes that are guaranteed not to cross-react with the reference genomes used during extraction.

The database is backed by compressed Roaring bitmaps that represent the full 4k-bit k-mer existence space, enabling O(1) membership queries across billions of k-mers with low memory overhead.

Features

K-mer Lookup

Paste k-mer sequences or upload a file to instantly check presence or absence in the barcode database. Results include GC content, nucleotide composition, and per-k-mer motif annotations.

Search Barcodes

Query the database with a substring and filter results by GC content range. Results are paginated with cursor-based navigation and can be downloaded as TSV. Reverse-complement search is supported.

Generate Barcodes

Generate random DNA barcodes matching specified length, GC content window, and motif filter constraints — independently of the database. Useful for simulation and benchmarking.

Motif Filters

All three tools support rich per-barcode motif filtering: homopolymer runs, low-complexity / Shannon entropy, restriction enzyme sites, functional sequence motifs, repeat detection (di-, tri-, tetranucleotide), and custom user-defined motif sequences.

Extraction Algorithm

Barcode extraction is performed by scanning reference genome FASTA files and recording every observed k-mer in a dense bit-array of 4k bits — one bit per possible k-mer, with standard ACGT base-4 encoding (A=0, C=1, G=2, T=3; leftmost nucleotide most-significant).

After processing all input sequences, the complement of the observed set (bits that remain unset) constitutes the candidate barcode space: k-mers with no exact match in the reference genomes. Extraction is parallelised across Slurm array tasks, each writing a partial bitarray shard; shards are then merged with a bitwise OR and converted to CRoaring portable format for compact storage and O(1) lookup at query time.

  • Encoding: GC-first base-4 encoding; all 4 strands of the k-mer encoded and the canonical (minimum) index stored.
  • Parallelism: Multi-threaded scanner with per-core shard accumulation to minimise lock contention.
  • Storage: Dense bitarray during extraction → CRoaring compressed bitmap for queries (flags = 1 for dense, 2 for Roaring in the KBITv1 file format).
  • Scalability: k=18 requires ~8 GB for the dense bitmap; Roaring compression typically reduces this by an order of magnitude for sparse barcode sets.
